# Synthesis notes

One Markdown file per area of the codebase or per complex external dependency, written in its own session so that an implementation session loads the summary instead of forty files (guide for agentic coding, perspectives 2 and 3). Each note starts with the date and the commit it describes, then: responsibilities, data flow, central types, non-obvious constraints, known pitfalls. Refresh a note when a retro or a review finds it stale; delete it when the area is gone. The issue stays the plan; these notes are context, never decisions.

Owner decision 2026-10-25 (ADR 0011, addendum of that date): a note is written by a session on tier `stark` (Opus) in its own session, never by a cheaper tier, because every implementer of the area trusts it. The first note comes after T1, when there is code to summarise. The main session names the note in the implementer's briefing (`Synthesis: docs/synthesis/<area>.md (date, commit)`, skill `brief-implementer`) and it is part of the review packet; the architecture reviewer flags a stale note, i.e. one whose date or commit is older than the area's last substantial change.
