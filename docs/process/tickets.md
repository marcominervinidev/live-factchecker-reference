# From plan to ticket

Short form for readers in the repo. Decision: ticket "Vom Plan zum Ticket" of the process map, `docs/spec/process/tickets.md` in the planning repo (2026-10-21). Files: `.github/ISSUE_TEMPLATE/{ticket,request}.md`, `.claude/skills/cut-tickets/SKILL.md`, `.claude/rules/tickets.md`, `.claude/agents/refinement.md`, `tools/evidence_table.py`.

## Levels

| Level | Carrier | What hangs on it |
|---|---|---|
| Increment | parent issue, tickets as native sub-issues | progress bar, frontier query, retro |
| Ticket | one issue from `ticket.md` | test design, critic, gate 1, manifest `.claude/frozen/<issue>.json`, acceptance cases, canary, judge, close, evidence table |
| Task | section of the ticket body | exactly one PR, branch `task/<issue>-<t>`, worktree, implementer briefing |

A sub-project in the guide's sense is a workspace (package or service): the commit scope, not a ticket level.

## Cutting

- A backend ticket ends at an observable seam (segment seam, live contract event, stage-3 API, harness report) and is accepted on stage 3 or in the harness. From the frontend increment on: tracer bullets through all layers, accepted on stage 4.
- No horizontal slices; a wide refactor goes as expand–contract. Order = architecture dependencies as native blocking edges. First ticket of an increment: the walking skeleton.
- Size: S = 1 task, M = 2–3 tasks, L is split before gate 1 (the refinement agent proposes the split). One task < 400 production lines.
- Way: skill `cut-tickets` (grill → slice → quiz → refinement agent per slice → owner reads → publish parent and sub-issues with edges). Matt's `to-tickets`, `to-spec`, `implement` are not called; `triage` handles intake.

## Template and evidence

Fields = the refinement draft (goal, numbered stable `AC<k>`, contracts, blast radius, revertibility, risk, size, session type, tasks with paths and verification command, open questions, sources), plus an optional **Measurement** section that turns the ticket into a measurement ticket (configuration, set, thresholds, budget; acceptance = harness comparison against `evals/reports/baseline.json` and the check "eval report present"; no judge, no canary).

The **evidence table** per AC (`AC | Tests (Stufe · Name) | Letzter Lauf | Richter | Bericht`) is generated by `tools/evidence_table.py` from the `@ac-<k>` tags, the Cucumber and Vitest JSON reports, the acceptance verdicts and the artifact links, and posted as an issue comment after every acceptance run and at close. Never by hand, never into the body. Playwright and Cucumber reports are Actions artifacts (30 days, owner only); nothing from `tests/acceptance/reports/` enters the repo.

References in a ticket, its comments and the gate-1 addenda are quoted, never bare: an `AC<k>`, a decision number, an ADR or another ticket is named together with the sentence it refers to (owner decision 2026-11-03, `CLAUDE.md` "Language").

## States and intake

Labels `needs-triage` → `needs-info` | `refined` → `ready-for-agent` (gate 1 passed) | `ready-for-human` | `wontfix`. In progress = assignee; closed by code after merge. New requirements enter through `request.md` with `needs-triage`; the owner runs the `triage` skill; the brief feeds the refinement agent. No prioritizer: the frontier of the blocking graph decides, the owner may name a ticket, `wontfix` is the kill switch. `ready-for-human` marks a ticket whose next task carries `Hand: owner` (the owner builds it; `docs/process/lernpfad.md`) and comes off when that PR is merged.

## Refinement after the first build

Judge "passt nicht" after merge keeps the ticket open; the refinement agent drafts the delta as a comment; a new task follows. AC or contract changes after gate 1 only by the owner with `FROZEN_UNLOCK`. A design shift first becomes an ADR addendum in the planning repo, then a new attempt. Anything new goes through intake with a link to the origin.

## Increment 1: scope and first cut

Scope: the detection pipeline in TypeScript from the segment seam to the live contract events, measured on the Golden Set in text mode through the harness. It rebuilds the arm confirmed in "Vergleichsprototyp" (#93, owner 2026-10-25): Haiku 5.5 with prompt v2 as Claim and Topic Extractor, Sonnet 5.5 as Resolver and as Verifier (ADR 0004, addendum 2026-10-25), on the Anthropic API directly (ADR 0006, addendum 2026-10-25). No client, no Check, no audio seam, no Speaker Mapper, no accounts, no Bedrock, no Vertex. The increment ends when `evals/reports/baseline.json` points at the first real run of the TypeScript pipeline. Re-cut on 2026-10-25 against the current ADRs and the work-system review (ADR 0011, addendum 2026-10-25).

### T1 mandatory list (operations minimum from T1, #120, 2026-10-23)

What cannot be retrofitted later belongs in the skeleton and in the service template (skill `new-service`) before the first service exists; what the operating model (#56) decides differently later (log sink, metrics stack, alerting) stays replaceable. Basis: ADR 0011 (twelve factors), `.claude/rules/platform.md`.

- **Structured JSON logging** as a stream to stdout, a module in `packages/`, mandatory in the service template. Fields: time, service, session id, event, duration, cost. Never transcript text, never names of private persons; retention per `docs/spec/datenschutz.md` section 2.
- **`/health` and `/ready`** per service; the edge and the stack tests use them (T1 acceptance: health through the edge).
- **Tokens and cost per model call** as a log event and as a metric, plus a counter per session ahead of the quota (ADR 0005); T7 delivers the values, the format is fixed here.
- **Release** paragraph in `docs/process/pr-format.md`: tag scheme `v0.x`, meaning of `main passed`, deployable image tag `:sha`, rollback = roll out the previous `:sha` again, `git-cliff` with the first tag.
- **Make targets** that hooks, workflows and docs already name: `acceptance`, `ci-secrets`, `ci-stack-up`, `ci-stack-down`, `test-api`, `test-e2e`, `lighthouse`, `hooks-install`, `up`, `dev`, `down`, `toolbox`, `stop`, `restart`, `secrets-init`, `test-unit`.
- **Scripts and files**: `scripts/tb`, `scripts/ci/affected.ts`, `scripts/ci/images.ts`, `scripts/check-contract-change.sh`, `.nvmrc`.

The same list stands in `docs/spec/process/tickets.md`; since the re-cut of 2026-10-25 it is split between T1 (what its own stages and the stage workflows need) and T1b (the rest; the release paragraph already stands in `docs/process/pr-format.md`). Together they are accepted only when every item exists or the ticket names it as deliberately deferred, with a reason.
